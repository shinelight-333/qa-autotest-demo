# Подробные тест-кейсы

Шесть примеров показывают подход к проектированию проверок. Все остальные сценарии перечислены
в [карте покрытия](coverage.md). Кейсы описывают ожидаемое поведение и существующий код;
этот документ не означает, что ручной или автоматизированный прогон выполнен заново.
Ожидаемые результаты основаны на [требованиях демо-магазина](requirements.md).

## TC-SMOKE-01 — Покупка с самовывозом и учебной оплатой

**Приоритет:** высокий. **Тип:** позитивный, UI + API.
**Автотест:** `test_purchase_pickup_and_demo_payment` в [smoke-наборе](../tests/ui/test_purchase_smoke.py).

**Предусловия:** локальный стенд работает; доступен `CAMP-PRICE-120` с ценой 120 ₽ и остатком
не меньше 1; создан новый покупатель и один адрес. Адрес нужен для обхода учебного UI-12,
но не должен передаваться в заказ с самовывозом.

1. Войти новым покупателем через UI.
2. Открыть карточку `CAMP-PRICE-120`, добавить одну единицу.
3. Перейти в корзину, проверить товар, количество 1 и сумму 120 ₽.
4. Открыть оформление с самовывозом. Проверить доставку 0 ₽.
5. Создать заказ и выполнить учебную оплату в UI.
6. Получить созданный заказ и корзину через API.

**Ожидается:** заказ `paid`, одна нужная позиция, сумма заказа и оплаты `120.00`,
доставка `pickup`, адрес `null`, корзина пуста.
Оплаченный заказ и пользователь остаются в учебной БД, товар расходуется.

## TC-API-01 — Другой покупатель не может прочитать чужой заказ

**Приоритет:** высокий. **Тип:** негативный, разграничение доступа.
**Автотест:** `test_api_01_foreign_order_is_not_readable` в [API-наборе](../tests/api/test_api_defects.py).

**Предусловия:** два новых покупателя A и B с отдельными HTTP-сессиями;
у A есть заказ с доступным `CAMP-MUG`.

1. Сохранить ID заказа A.
2. В сессии B выполнить `GET /api/v1/orders/{id}/` с этим ID.
3. Получить список собственных заказов B.

**Ожидается:** HTTP `404`, поле `items` с содержимым заказа не возвращается,
список заказов B пуст. В cleanup новый заказ A отменяется.

## TC-API-03 — Сервер отклоняет цену, переданную клиентом

**Приоритет:** высокий. **Тип:** негативный + контрольный позитивный запрос.
**Автотест:** `test_api_03_client_price_is_rejected` в [API-наборе](../tests/api/test_api_defects.py).

**Предусловия:** новый покупатель; в корзине одна единица `CAMP-PROMO`;
известны исходные корзина и остаток.

1. Отправить `POST /api/v1/orders/` с `delivery_method: pickup` и дополнительным полем
   `items: [{product_id: <ID>, unit_price: "1.00"}]`. Использовать CSRF и новый `Idempotency-Key`.
2. Проверить ответ, список заказов, корзину и остаток.
3. Создать заказ обычным запросом без клиентского `items`.

**Ожидается:** первый запрос возвращает HTTP `400` и ошибку поля `items`;
заказ не создан, корзина и остаток не изменены. Контрольный запрос создаёт заказ
с серверной ценой товара. Новый заказ отменяется при cleanup.

## TC-API-12 — Истёкший промокод отклоняется на обоих этапах

**Приоритет:** высокий. **Тип:** негативный, параметризация `quote` / `order`.
**Автотест:** `test_api_12_expired_promo_is_rejected` в [API-наборе](../tests/api/test_api_defects.py).

**Предусловия:** новый покупатель; одна единица `CAMP-PROMO` в корзине;
`OLD10` существует и уже истёк. Сохранены корзина и остаток.

1. Для варианта `quote` отправить `POST /api/v1/checkout/quote/` с `pickup` и `OLD10`.
2. В отдельном тестовом случае для варианта `order` отправить `POST /api/v1/orders/`
   с тем же промокодом, CSRF и новым `Idempotency-Key`.
3. Для каждого варианта проверить ответ, заказы, корзину и остаток.

**Ожидается в каждом случае:** HTTP `400`, код `PROMO_INVALID`, заказов нет,
корзина и остаток сохранены. Это два независимых автоматизированных случая.

## TC-API-14 — Отмена заказа возвращает последнюю единицу

**Приоритет:** высокий. **Тип:** переход состояния и проверка побочных эффектов.
**Автотест:** `test_api_14_cancellation_restores_last_unit` в [API-наборе](../tests/api/test_api_defects.py).

**Предусловия:** новый покупатель; `CAMP-LAST` доступен с остатком **ровно 1**.

1. Добавить товар в корзину.
2. Создать заказ с самовывозом.
3. Через API проверить остаток 0.
4. Отменить созданный заказ через `/orders/{id}/cancel/`.
5. Проверить статус заказа и остаток товара.

**Ожидается:** статус `cancelled`, остаток снова 1.
Если исходный остаток уже 0, сценарий нельзя считать воспроизведённым:
нужно подготовить данные и повторить запуск.

## TC-UI-09 — В заказ сохраняется выбранный адрес

**Приоритет:** высокий. **Тип:** позитивный, согласованность UI и API.
**Автотест:** `test_ui_09_checkout_sends_selected_address` в [UI-наборе](../tests/ui/test_ui_defects.py).

**Предусловия:** новый покупатель вошёл в UI; через API созданы два адреса:
основной в Москве и второй в Туле на улице Походной; `CAMP-MUG` добавлен в корзину.

1. Открыть оформление заказа.
2. Выбрать курьерскую доставку.
3. Выбрать второй адрес — Тула.
4. Подтвердить заказ, сохранить его ID.
5. Получить заказ через API и сравнить снимок адреса со вторым адресом.
6. Проверить адрес в UI страницы заказа.

**Ожидается:** получатель, телефон, город, улица, дом, квартира и индекс совпадают
с выбранным вторым адресом; в UI показано «Тула, Походная».
Новый неоплаченный заказ отменяется при cleanup.
